[14] When is throwing an exception preferable to returning an “error value”? 
    The basic idea is that if a function finds an error that it cannot handle, 
    and it doesnt return normally, returning an error value might not have 
    any effect, (e.g., a function returning any possible int can't use -1 as an error).
    The caller might ignore the a return value. Instead, it throw an expection indicating
    what went wrong. Any direct of indirect vall can catch the expection, that is, specifiy
    what to if the called code throw an exception.

[15] When is returning an “error value” preferable to throwing an exception?
    *When the error is a normal, expected outcome (not truly exceptional), 
    e.g., returning -1 when a search finds nothing.
    *The main function can use error value because there 
    is no caller to handle the exception.
    *When the caller is right there and will always check, it is a simple and 
    local a value check is simpler than using try/catch
    *When performance is critical, exceptions have overhead; error values are faster.

[16] Describe the process of how exceptions are thrown and caught.
    Thorwing: When a function detects an error it cannot handle, it 
    uses keyword throw to create an expection object and stop normal 
    execuation. The runtime then unwinds the call stack, detroying local 
    variables, until finds a matching catch.

    Catching: Code that might throw is wrapped in a try block. After it, 
    one or more catch block specifiy what expection type to handle.

    int area(int len, int wid){
        if(len <=0 || wid <=0){
            throw runtime_error("Enter positive value for len and wid")
        }
            return len*wid;
    }

    int main(){
        try{
            cout<<"area:"<<area(-1,2);
        }
        catch(runtime_error& e){
            crr << e.what() << "\n";

        }
    }

    1. throw runtime_error("bad input"): creates the exception object and 
    exits the function immediately.
    2. The runtime unwinds the stack: exits each function on the call stack, 
    cleaning up local variables (destructors run).

    3. It searches up the call stack for a try block with a matching catch.

    4. If found: the matching catch block runs.
    
    5. If not found: std::terminate() is called and the program aborts.

[21] When would you not test a postcondition? 
    -when the check is too expensive
    -when the result is trivially correct by design, a function simply returns
